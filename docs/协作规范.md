一、全栈团队协作理念与工具链
1.1 全栈团队协作模式
核心原则：模块化全栈开发
- 团队成员均为全栈工程师，按业务模块拆分核心职责
- 每人负责1-2个完整模块的前后端全流程开发
- 跨模块相互补位，优先保障核心流程闭环
- 非核心功能按优先级弹性调整，提升整体开发效率
迭代节奏：每周循环
- 周一：任务认领，开发启动
- 周三：站会同步，问题识别
- 周六：迭代评审，下周规划
- 周日：集成部署，代码合并
1.2 统一工具链
- 开发环境：Cursor / VSCode / Antigravity
- AI 开发工具：Claude Code + 88code (或其他优质中转) + Speckit
- 原型设计工具：Antigravity / Claude Code + cliproxy + packycode
- 版本控制：Git + GitLab (企业自建)
- 项目管理：飞书多维表格 (Scrum 项目管理)
- 沟通协作：飞书项目群

3.2.2 数据库设计与表结构管理
本项目采用开发环境与生产环境分离的数据库管理策略：
- 开发环境（本地 + dev 服务器）：使用 synchronize: true 自动同步表结构，快速迭代
- 生产环境：使用 Migration 管理表结构变更，安全可控
一、开发环境：自动同步模式
配置方式：
TypeOrmModule.forRoot({
  synchronize: process.env.NODE_ENV !== 'production',  // 开发环境自动同步
  migrationsRun: process.env.NODE_ENV === 'production', // 仅生产环境执行 Migration
});
开发流程：
1. 直接修改 Entity 文件（新增/修改/删除字段）
2. 重启服务，TypeORM 自动同步表结构到本地数据库
3. 提交 Entity 代码到功能分支
4. 如有重大表结构变更，在飞书群通知相关模块负责人
团队成员操作：
git pull origin develop
npm run start:dev  # 启动服务时自动同步表结构
注意事项：
- 开发环境数据为测试数据，同步导致的数据丢失可接受
- 每人使用独立的本地数据库，避免相互影响
- 删除字段/表前，先在群内通知，避免影响其他模块开发
- dev 服务器环境也使用自动同步模式，确保团队成员使用相同的表结构
数据初始化（Seed）：
- synchronize 只同步表结构，不会自动填充数据
- 对于必要的基础数据（如管理员账号、角色权限、系统配置等），需要使用 Seed 进行初始化
- 使用 AI（Claude Code）编写 Seed 脚本，推荐使用 typeorm-extension 库
- 团队成员首次启动项目后，执行 npm run seed 初始化必要数据
- Seed 脚本应确保幂等性（可多次执行而不产生重复数据）
二、生产环境：Migration 模式
部署到生产环境时，必须使用 Migration 管理表结构变更，确保数据安全和可回滚。
🚫 禁止使用 migration:generate 命令
所有 Migration 由 AI（Claude Code）手动编写，确保代码质量。
⚠️ 明令禁止直接操作生产环境数据库表结构：
- 严格禁止 - 使用 SQL 命令（如 ALTER TABLE、CREATE TABLE、DROP TABLE）直接修改生产环境表结构
- 严格禁止 - 使用任何图形化工具（如 Navicat、DataGrip）手动修改生产环境表结构
- 必须遵守 - 生产环境的所有数据库结构变更（包括表、字段、索引、外键）必须且只能通过 Migration 完成
- 数据操作 - 生产环境禁止手动操作数据
核心原则：
- 原子化操作 - 拆分为多个小的独立脚本，方便回滚
- 时间戳命名 - 文件名格式：<timestamp>-<描述>.ts（如 1234567890123-AddUserEmail.ts）
- KISS 原则 - 保持简单，避免复杂操作
- 完整性保证 - up() 必须有对应的 down() 方法
命名示例：
✅ 1234567890123-AddUserEmailField.ts
✅ 1234567890124-CreateOrdersTable.ts
❌ 1234567890123-UpdateDatabase.ts  # 描述不清晰
生产部署流程：
1. 修改 Entity - 在 Entity 文件中新增/修改字段
2. AI 创建 Migration - AI 自动生成带时间戳的 Migration 文件
3. 测试 - 执行 npm run migration:run 验证
4. 发送通知 - 在飞书群通知相关模块负责人（详见下文 3.2.5 节）
特殊场景：
场景
处理方式
修改字段类型
AI 编写数据迁移逻辑，确保旧数据正确转换
删除字段/表
⚠️ 先在群内讨论确认，再删除
复杂变更
拆分为多个 Migration，每个只做一件事
3.2.3 AI 辅助全栈开发
1. 模块架构设计
向 Claude Code 提问（自动触发对应技术栈的 Skill）：
我们正在开发一个 [业务模块] 模块，采用全栈开发模式：
- 后端：NestJS + TypeORM + PostgreSQL
- 前端：Vue3 + TypeScript + TailwindCSS
请帮我设计这个模块的完整架构，包括：
- 前后端目录结构
- Entity 设计（字段、类型、关系）
- 后端 Service、Controller、DTO 设计
- 前端页面、组件、路由设计
- 接口设计（RESTful API）
2. 后端代码生成
根据架构设计，AI 生成完整的后端代码：
- Entity 文件（带装饰器、字段定义、关系）
- Service 文件（业务逻辑、数据库操作）
- Controller 文件（接口定义、请求处理）
- DTO 文件（数据传输对象）
- Module 文件（模块配置）
3. 前端代码生成
基于已完成后端接口，AI 生成前端代码：
- 页面组件（Vue 3 Composition API）
- 路由配置
- API 调用封装
- 状态管理（Pinia）
- 样式设计（TailwindCSS）
4. 接口文档生成
AI 自动生成 Swagger 注释，生成标准 API 文档：
/**
 * @description 获取用户列表
 * @param {number} page 页码
 * @param {number} size 每页数量
 * @returns {User[]} 用户列表
 */
@Get()
async getUsers(@Query('page') page: number, @Query('size') size: number) {
  return this.userService.findAll(page, size);
}

- ✅ 安全漏洞（SQL注入、XSS、权限控制等）

- AI 代码审查已完成
- 安全问题已全部修复
- 严重性能问题已修复
- 主要建议已处理（必须修复的已改，可选的已评估）

- 功能完整，本地测试通过

- 无法达成一致时，由团队负责人决策

2.1 文档管理理念
核心原则：文档即代码（Docs as Code）
由于项目迭代周期快，我们采用"文档即代码"的方式管理文档：
- 文档与代码同步 - 文档存放在代码仓库中，与代码一起进行版本管理
- 代码注释生成文档 - API 文档通过代码注释自动生成，无需手动维护
- 文档重在指引 - 文档说明架构思路、设计原则、功能位置，而非复制代码实现
- 保持文档简洁 - 避免冗长描述，通过代码位置引用让开发者直接查看实现
文档撰写要求：
✅ 应该写：
- 模块功能概述和职责
- 架构设计思路和原则
- 关键逻辑的代码位置引用（如 见 src/modules/user/user.service.ts:45）
- 数据流向和模块间交互说明
- 特殊处理逻辑的原因说明
❌ 不应该写：
- 复制粘贴具体代码实现
- 详细的函数调用步骤（代码已说明）
- 写死的接口参数和返回值（易过时，应从代码注释生成）
